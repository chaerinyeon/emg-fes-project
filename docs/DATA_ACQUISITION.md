# 데이터 획득 — FES 자극 타이밍과 측정 방법

**기준일:** 2026-07-17 ·

이 문서는 "지금 어떻게 데이터를 얻고 있는가"를 기록한다. 값은 **설계값(코드에 적힌 것)** 과
**실측값(raw 에서 직접 잰 것)** 을 구분해 적는다. 둘이 어긋나는 곳이 실제로 있다.

---

## 1. 하드웨어 구성

```
 [전극 3개]
     │
 [MyoWare 2.0 Muscle Sensor]  ── SIG(RAW) ──►  GPIO36 (A4)
     │
 [MyoWare 2.0 Wireless Shield]  = ESP32-WROOM 내장
     │  BLE GATT (Nordic UART 호환)
     ▼
 [iPhone — Flutter 앱]
     │  USB 동기화
     ▼
 [Mac  ~/emgfes-data/subject_<id>/]


### ⚠️ 중요 — 자극 파형은 우리가 만들지 않는다

펌웨어는 FES 의 **물리 버튼을 릴레이로 누를 뿐**이다
(`triggerStimulation()` 은 ON/OFF 핀을 150ms HIGH → 짧게 누름, OFF 는 2초 long-press).

즉 **주파수·펄스폭·버스트 타이밍은 전부 자극기의 내장 프로그램**이고, 코드에는 그 값이
존재하지 않는다. "세기 5" 는 UP 버튼을 5번 누른 상태를 뜻한다.
→ 아래 §2 의 타이밍은 **설계값이 아니라 기기를 관측해서 알아낸 값**이다.

## 2. FES 자극 타이밍 (전부 실측)

`raw` 1kHz 에서 `|c| > 400` (DC 제거 후) 문턱을 넘는 시점을 자극으로 검출해 측정.
**두 세션이 완전히 동일** → 기기가 일정하게 동작한다.

```
 ◄────────── 1621.9ms 주기 ──────────►
 ████████████████████         ·········
 ◄─── 593ms 버스트 ──►◄─1029ms 쉼─►
   펄스 20개, 간격 31.185ms (32.078Hz)
```

| 항목 | 실측값 | 비고 |
|---|---|---|
| 버스트 내 펄스 간격 | **31.185ms** → **32.078Hz** | ⚠️ 중앙값 31ms 가 아니라 **평균**. 아래 경고 참조 |
| 버스트당 펄스 수 | **20개** | |
| 버스트 지속 | **593ms** | 19 × 31.185ms ≈ 592.5ms |
| 버스트 사이 쉼 | **1029ms** | 범위 1028~1030ms |
| **버스트 주기** | **1621.9ms** | 선형적합. 033307 σ=**0.58ms**, 범위 1621~1623ms |
| 주기 드리프트 | **+1 ppm/버스트** | 세션 전체(184버스트) 누적 **0.3ms** → 사실상 없음 |
| Duty | **37%** | |
| **평균 자극률** | **12.35 /초** | 20펄스 ÷ 1.6219초 = 12.35 ✓ |

검증: 042118 = 7,356자극/596초 = 12.35/s · 033307 = 3,680자극/298초 = 12.36/s

**기기는 잠금(locked) 수준으로 안정적이다.** 033307 은 버스트 주기 표준편차가 0.58ms 이고 세션
전체 드리프트가 0.3ms 다. 창을 주기에 정렬해도 세션 내내 어긋나지 않는다는 뜻 —
드리프트 보정은 불필요하다.
(042118 의 σ=6.5ms 는 이상치 1개(1496ms) 탓이며, 자극 검출이 버스트 하나의 앞 4펄스를 놓친 것으로 보인다.)

> ### ⚠️ 펄스 주파수는 32.3Hz 가 아니라 **32.078Hz** 다 — 양자화 착시
>
> ISI **중앙값**은 31ms 인데, 이건 1kHz 샘플링의 1ms 양자화 때문에 정수로 떨어진 값이다.
> `1000/31 = 32.258` 이 그래서 나왔다. 진짜는 ISI **평균 31.185ms → 32.078Hz**.
>
> 60초 FFT(분해능 0.017Hz)로 확인: 배음 봉우리가 64.2 · 96.2 · 128.3 · 160.4 · … · 449.1Hz,
> **간격 32.08Hz**. (k=1 은 대역 하한 20Hz 근처라 안 잡힘)
>
> **영향:** `session_overview.py` 의 `F0 = 32.26` 은 오차 0.182×k → **k=14 에서 2.55Hz** 라
> ±2Hz 노치가 놓친다. 노치가 걷어내는 대역전력이 **81.1% → 68.9%** 로 12%p 손해.
> → `F0` 를 **32.08** 로 고칠 것.

> **기존 독스트링의 "1.61초마다 0.49초 버스트" 는 버스트 길이가 틀렸다.**
> 주기 1.62초는 맞으나 버스트는 0.49초가 아니라 **0.593초**다.
> (`mwave_trend.py` · `session_overview.py`)

### 자극 하나의 시간 구조 (raw 1kHz, 자극동기 평균으로 관측)

이 구조가 모든 분석의 근거다. 자세한 건 [`fatigue_2sigma`/M-wave 분석 노트] 참조.

| 구간 | 정체 | 쓰임 |
|---|---|---|
| **0~1ms** | 용량성 자극 스파이크 | **순수 자극 — 근육 반응이 물리적으로 불가능.** 대조군은 반드시 여기서 |
| 2~4ms | M-wave 시작부 | ⚠️ 근육 신호. 대조군으로 쓰면 안 됨 |
| **5~15ms** | **M-wave** (유발반응) | 피로 지표의 본체 |
| 16~30ms | 자발 EMG 만 있는 깨끗한 창 | 자발 **RMS** 는 여기서. **MDF 는 불가**(§5 참조) |

### 🔑 자발 EMG 는 버스트 안에만 있다 — 쉼 구간은 비어 있다

"쉼 구간(1029ms)이 깨끗하니 거기서 RMS/MDF 를 재면 되지 않나" 는 **안 통한다.**

| | 쉼 구간(1029ms) RMS | 버스트 내 16~30ms 창 RMS |
|---|---|---|
| 무부하 (힘 0) | 24.3 | 21.6 |
| 유부하 (힘 줌) | **24.0** | **30.9** (+43%) |

쉼 구간은 **무부하와 유부하가 같다**. 프로토콜이 "FES 버스트에 맞춰 힘"이라 사람이 버스트 사이엔
완전히 쉬기 때문이다 → **쉼 구간엔 자발 정보가 0.**
자발 신호가 있는 곳은 **버스트 안 펄스 사이 16~30ms 창뿐**이고, 그건 **15ms 조각**이다.

## 3. 측정 프로토콜 (현재)

```
 1. FES 를 먼저 켠다 (세기 5 고정)          ← 손으로. 펌웨어가 켜지 않는다
 2. 앱에서 스타트 → 기록 시작 + 15초 카운트다운 팝업
 3. 0~15초 : 힘 빼고 대기                    ← 무부하 구간
 4. 15초   : rest_end 마커 자동 기록 + "이제 힘을 주세요"
 5. 15초~끝 : FES 버스트에 맞춰 일정한 힘
 6. 중간에 힘들면 easy / medium / hard 를 탭
 7. 정지   → env(10Hz) + raw(1kHz) + emg(1Hz) CSV 저장
```

**왜 무부하 15초를 먼저 두나:** 유부하 baseline 을 잡기 위해서다. 무부하 구간이 baseline 에
섞이면 조건이 다른 데이터가 기준이 된다. `rest_end` 마커가 그 경계를 표시한다.

**왜 FES 를 먼저 켜나:** 자극이 이미 안정된 상태에서 기록을 시작해야 초반 블록을 기준으로 쓸 수 있다.

## 4. 저장되는 파일 3종

한 세션이 **세 해상도로 동시에** 저장된다. 아래로 갈수록 가볍고, 해석이 더 얹히고, **되돌릴 수 없다.**

| 파일 | 속도 | 행수(596초 기준) | 크기 | 내용 |
|---|---|---|---|---|
| `raw_*.csv` | **1000Hz** | 595,700 | 6.7M | `Time(ms), Raw_ADC` — **해석 없는 원신호** |
| `env_*.csv` | 10Hz | 5,363 | 268K | 펌웨어가 계산한 지표 + `Marker` |
| `emg_*.csv` | 1Hz | 599 | 56K | 앱의 판정 상태 + `wall_time` |

```
raw : 무슨 일이 실제로 일어났나   (해석 없음)
env : 기기가 뭘 봤다고 생각했나
emg : 앱이 그래서 뭘 하기로 했나
```

- `env`/`emg` 의 `Raw_ADC`/`emg_raw` 는 **raw 와 다른 스트림**이다(평활된 값, 소수).
  raw 첫 행 `1790`(정수) vs env 첫 행 `1893.0`.
- `emg` 는 `env` 를 더 솎은 것(앞 200행 중 148개가 env 에 그대로 존재) + 앱 상태 컬럼.
- 시간축: `raw`/`env` 는 세션 시작부터의 상대시간(0부터), `emg` 만 `wall_time`(실제 시각) 보유.

### ⚠️ raw 가 유일하게 쓸모 있는 파일이다

M-wave 를 올바르게 얻을 수 있는 소스는 **raw 뿐**이다.

- 0~1ms 스파이크와 5~15ms M-wave 를 가르려면 ms 해상도가 필요하다. 10Hz(=100ms)로는
  자극 하나가 통째로 한 칸에 뭉개진다.
- `env` 의 `MW_Amp`/`MW_Area`/`MW_Latency`/`MW_Valid` 는 펌웨어 잠복 게이트 버그로 **거의 전부 무효**다
  (042118: 5,363행 중 `MW_Valid=1` 이 **1행**). 쓰지 말 것.
- `env` 의 `RMS` 는 `STIM_BLANK_MS = 5` 라 M-wave(5~15ms)가 그대로 섞여 들어간다
  → 자발 EMG 가 아니라 **M-wave 의 희석된 대리지표**다.
- `env` 에서 믿을 수 있는 칸은 사실상 **`Marker`** 뿐이다.

**env·emg 만 있는 세션은 기기의 (틀린) 해석만 남고 원본이 없어 재분석이 원천 불가능하다.**

## 5. 펌웨어의 RMS/MDF/blanking — 전부 자극 격자와 어긋나 있다

**요약: 펌웨어의 RMS 와 MDF 는 근육을 재고 있지 않다.** 코드의 산술은 대체로 맞다.
틀린 건 **창과 게이트를 자극의 시간 구조에 맞추지 않은 설계**다.

### 5.1 blanking 이 자극의 절반만 덮는다 (버그)

blanking 은 `mwArtifactAtMs`(M-wave 아티팩트 검출 시각)에 의존한다.
그런데 그 검출기에 **`MW_REFRACTORY_MS = 40`** 이 걸려 있고 **자극 주기는 31.185ms** 다.
40 > 31 → 하나 잡으면 다음 자극(31ms 후)은 불응기에 막히고, 그 다음(62ms 후)에야 잡힌다.

**게이트가 두 개 겹쳐 있다.** `mwCapturing` 상태머신도 검출 후 `since > MW_WINDOW_END_MS(30)`
까지 true 라, 31ms 뒤 자극은 `!mwCapturing` 조건에도 막힌다. **불응기만 고치면 안 된다.**

펌웨어 상태머신을 raw 에 그대로 재현한 결과:

| | 042118 | 033307 |
|---|---|---|
| 실제 자극 | 7,356 | 3,680 |
| 펌웨어가 검출 | 3,678 (**50.0%**) | 2,111 (57.4%) |
| 검출 간격 최빈값 | **62ms** (= 자극 2개마다 하나) | 62ms |
| blanking 이 덮은 자극 | **50.0%** | 44.7% |
| blank 표본 비율 | 3.09% | 3.55% |

- 이상적: 5ms × 12.35/s = **6.2%** → 실제는 그 절반
- **놓친 자극의 스파이크 크기 중앙값 1595 ≈ 잡힌 것 1594** → 문턱 문제가 **아니라** 순전히 불응기
- **모델 검증:** 이 로직으로 RMS 재현 → **167.4 vs 실측 env 168.0 (오차 0.4%)**,
  033307 은 290.3 vs 295.1 (1.6%). 시뮬레이션이 실물을 재현한다

또 hold 방식(`procCentered = lastCleanCentered`) 자체가 스펙트럼에 **31ms 주기 계단 함수**를
만든다. 코드 주석의 *"→ RMS/MDF 가 자극에 오염되지 않는다"* 는 **사실이 아니다.**

### 5.2 그래서 RMS 의 90% 이상이 근육이 아니다

전력 기준 분해 (유부하 20~44초):

| 성분 | 042118 | 033307 |
|---|---|---|
| **놓친 자극 스파이크** | **76%** | **55%** |
| M-wave (5~15ms) | 15% | 41% |
| **진짜 자발 EMG** | **9%** | **4%** |

→ 펌웨어 RMS 의 **91~96% 가 자극 스파이크 + M-wave**. 무부하와 유부하 차이가 +5% 뿐인 이유다.

**결과적으로 SPC 의 RMS 규칙은 구조적으로 발동할 수 없다.**
펌웨어 RMS 는 사실상 유발반응의 대리지표인데, 유발반응은 피로에서 **내려간다.**
그런데 SPC 규칙은 `RMS > UCL` — **올라가야** 발동한다.
실측: 042118 RMS **−11.8%**(ρ=−0.62) → **후보 0개**. 규칙이 신호를 반대 방향으로 보고 있다.

### 5.3 MDF — 창이 버스트보다 짧다

`FFT_SIZE = 512` → **512ms 창**. 그런데 버스트가 **593ms**, 주기가 **1621.9ms** 다.
창이 버스트보다 짧아서, **버스트 안에 통째로 들어가거나 쉼에 통째로 들어간다.**
→ 100ms 마다 **무엇을 재는지 자체가 바뀐다.**

실측 (042118 유부하 4,861행):
- MDF 분포가 **이봉(bimodal)** — 57~75Hz 에 811개 vs 128~182Hz 에 2,897개
- 자기상관 봉우리가 **lag 1.5초** (= 자극 주기 1.62초)
- 인접 100ms 간 **20Hz 초과 점프가 26%**, 최대 197Hz
- MDF 범위 57~272Hz

여기에 더해:

1. **자극 배음을 안 걷어낸다.** `MDF_NOTCH_HZ[] = {60, 120, 180}` — 전원 노이즈만 판다.
   32.078Hz 배음(64·96·128·…·449Hz)이 대역전력의 **81%** 인데 그대로 남는다.
2. **bin 양자화, 보간 없음.** `return (float)i * BIN_HZ;` — bin = 1000/512 = **1.953Hz**.
   baseline σ 가 0.74 bin 으로 붕괴해 SPC 가 헤어트리거 되는 원인.
3. **실패를 0 으로 반환.** `if (totalPower <= 0.000001) return 0;` — 0Hz 가 유효값처럼 보인다.
   다운스트림이 `MDF > 0` 으로 걸러 살아남았을 뿐.

### 5.4 창이 자극 격자의 정수배가 아니다

| | 현재 | 주기(1621.9ms) 대비 |
|---|---|---|
| RMS 창 | 1000ms | **0.62 주기** |
| MDF 창 | 512ms | **0.32 주기** |

정수배 후보: **1622 / 3244 / 4866ms**.
단 **주기 ÷ 펄스간격 = 51.98** 로 정수가 아니라, 버스트 격자에 맞춰도 펄스 격자에는 안 맞는다.
둘을 동시에 만족하는 창은 없다.

### 5.5 수정 순서 (순서가 중요하다)

**1·2 를 고치지 않은 채 4·5 를 손대면 아무것도 나아지지 않는다.**

| # | 무엇 | 어디 | 왜 |
|---|---|---|---|
| 1 | `MW_REFRACTORY_MS` **40 → 25 이하** | 펌웨어 | 자극주기 31ms 미만이어야. 검출률 50%→100%, blanking 정상화, M-wave 표본 2배. **효율 최대** |
| 2 | `mwCapturing` 해제를 blanking 게이트와 **분리** | 펌웨어 | 1번만 고치면 두 번째 게이트가 남는다 |
| 3 | `F0` **32.26 → 32.08** | `session_overview.py` | 노치 81% vs 69% |
| 4 | `STIM_BLANK_MS` **5 → 16** | 펌웨어 | M-wave 를 RMS 에서 제외. **1·2 이후에만 의미 있음** |
| 5 | RMS 창 **1000 → 1622ms** | 펌웨어 | 주기 정수배 |
| 6 | MDF 배음 노치 추가 (`32.078·k ± 2Hz`) | 펌웨어 | 전원 노이즈만 파는 건 절반짜리 |
| 7 | MDF 보간 추가 / 실패 시 0 대신 NaN | 펌웨어 | 양자화·오해석 방지 |

1·2 는 **M-wave 잠복 게이트 수정(§7)과 같은 검출기를 건드린다** → 함께 처리할 것.

### 5.6 자발 MDF 는 프로토콜을 바꿔야 얻는다

위를 다 고쳐도 **자발 EMG 의 MDF 는 이 프로토콜에서 측정 불가에 가깝다.**
자발 신호가 있는 곳은 15ms 조각(펄스 사이 16~30ms)뿐이라 주파수 분해능이 66Hz 다.
쉼 구간(1029ms)은 길지만 §2 에서 봤듯 **자발 정보가 0** 이다.

→ MDF 를 원하면 **"버스트에 맞춰 힘" 대신 "연속으로 힘 유지"** 로 프로토콜을 바꿔야 한다.
그러면 쉼 1029ms 가 깨끗한 자발 EMG 창이 된다 (1024-point FFT, bin 0.98Hz).
**이건 코드가 아니라 측정 설계의 문제다.**

## 8. 알려진 문제

### 획득 (프로토콜·하드웨어)

| 문제 | 상태 | 영향 |
|---|---|---|
| **악력이 측정되지 않음** | 미해결 | "일정한 힘"은 프로토콜상 **가정**일 뿐. 피로 해석의 가장 큰 구멍 |
| **raw 미저장 세션 다수** | 미해결 | 78세션 중 raw 는 6개. 나머지는 재분석 불가 |
| `rest_end` 마커가 2세션뿐 | 신 프로토콜 적용 중 | 그 이전 세션은 유부하 baseline 불가 |
| **`hard` 가 '세션 종료'와 교락** | 미해결 | hard 25개의 종료까지 중앙값 **21.8초**, 마지막 마커가 hard 인 세션 17/23 → "hard = 이제 그만" 신호. 학습 타깃 불가 |
| `easy` 라벨 n=1 | 미해결 | 클래스가 사실상 없음 (easy 1 / medium 16 / hard 25) |
| **자발 MDF 측정 불가** | 프로토콜 문제 | 버스트에 맞춰 힘주니 쉼 구간이 비어 있음 → 자발 신호가 15ms 조각뿐 (§5.6) |

### 신호처리 (펌웨어·스크립트)

| 문제 | 상태 | 영향 |
|---|---|---|
| **`MW_REFRACTORY_MS = 40` > 주기 31ms** | 미해결 | **자극의 50% 만 검출** → blanking 도 절반만. 놓친 스파이크가 RMS 전력의 **76%** (§5.1) |
| **`mwCapturing` 이 두 번째 게이트** | 미해결 | 불응기만 고쳐도 31ms 뒤 자극이 여전히 막힘 (§5.1) |
| 펌웨어 M-wave 잠복 게이트 | 미해결 | `MW_WINDOW_START_MS=5` vs `MW_LAT_MIN_MS=6` 모순 → `MW_Valid` ≈ 0% |
| **MDF 창(512ms) < 버스트(593ms)** | 미해결 | MDF 가 **이봉 분포**, 100ms 마다 재는 대상이 바뀜 (§5.3) |
| MDF 가 자극 배음을 안 걷어냄 | 미해결 | 전원 노이즈만 노치. 배음이 대역전력의 **81%** (§5.3) |
| `STIM_BLANK_MS = 5` | 미해결 | M-wave 가 RMS 로 새어 들어감. **단 §5.1 을 먼저 고쳐야 의미 있음** |
| RMS 창 1000ms | 미해결 | 주기(1621.9ms)의 0.62배 → duty-cycle 에 휘둘림 (§5.4) |
| MDF bin 양자화, 보간 없음 | 미해결 | bin 1.953Hz. baseline σ 붕괴 → SPC 헤어트리거 (§5.3) |
| `session_overview.py` `F0 = 32.26` | 미해결 | 진짜는 **32.078**. 양자화 착시. 노치 81%→69% (§2) |
| hold 방식 blanking | 미해결 | 31ms 주기 계단 함수를 새로 만듦. 주석의 "오염되지 않는다"는 사실 아님 (§5.1) |

### 다음 세션부터 바꿀 것 (획득)

1. **raw 1kHz 를 항상 저장** — 이것 하나가 데이터셋 크기를 정한다
2. **`rest_end` 마커 필수**, 세션 **≥ 10분** 고정
3. **악력 독립 채널 로깅** — 없으면 M-wave 해석에 늘 구멍이 남는다
4. **난이도 라벨을 고정 간격 프롬프트로** — 자발적 탭은 희소하고(37%), easy 가 안 찍히고,
   종료와 교락된다. 60초마다 물으면 셋이 한 번에 해결된다
5. **0~1ms 스파이크 드리프트를 세션 품질 지표로 로깅** — |Δ| > 10% 면 M-wave 해석 신뢰도 저하

### 코드 수정 순서

§5.5 참조. 요약하면 **`MW_REFRACTORY_MS` 40→25 와 `mwCapturing` 게이트 분리가 먼저**이고,
`STIM_BLANK_MS`·RMS 창·MDF 노치는 그 다음이다. 순서를 뒤집으면 아무것도 나아지지 않는다.
1·2 는 M-wave 잠복 게이트 수정과 **같은 검출기**를 건드리므로 함께 처리한다.
