# 모니터링 웹 분리 설계안 — 폰이 서빙하는 로컬 관찰 화면

- 작성일: 2026-08-04
- 브랜치: `feature/game`
- 대상: `flutter_app` (RE-FIT) + `docs/spc_stamina_monitor.html`
- 선행 문서: [2026-08-03-realtime-catch-game-design.md](2026-08-03-realtime-catch-game-design.md)
  — 신호 파이프라인(`LiveFatigueFeed` / `SigmaTracker` / `FatigueZone`)을 그대로 계승한다.

## 1. 목적

환자는 폰에서 캐치 게임을 하고, **치료사·관리자는 옆에서 노트북 브라우저로 같은
세션을 실시간 관찰**한다. 지금은 관찰 화면이 폰 안에 있어서 둘을 동시에 볼 수 없다.

관찰자가 세션 중에 실제로 답을 원하는 질문은 넷이다.

1. 지금 위험한가 (σ·존)
2. 얼마나 왔나 (경과·수축 횟수·2σ→3σ 리드타임)
3. 이 신호를 믿어도 되나 (연결·신호품질)
4. 환자가 지금 뭘 하고 있나 (게임 상태·휴식 여부)

화면은 이 넷에 답하는 것만 기본으로 보여준다. RAW 오실로스코프를 상시 띄우면
판단이 아니라 노이즈가 늘어난다 — 접이식 진단 패널로 내린다.

## 2. 확정된 결정과 그 근거

| 항목 | 결정 | 근거 |
|---|---|---|
| 전송 경로 | ESP32 → **BLE → 폰 → Wi-Fi(WebSocket) → 브라우저** | 펌웨어 무수정. §2.1 |
| 망 범위 | 같은 Wi-Fi(로컬)만. 전송 계층은 교체 가능하게 | 지연·보안·비용 전부 유리. 원격은 나중에 중계만 추가 |
| 웹의 권한 | **보기 전용** (+ RAW 구독 토글) | "정지는 사용자 STOP만" 원칙 유지 |
| 웹앱 형태 | **단일 정적 HTML**, 폰이 직접 서빙 | 배포·호스팅·빌드툴체인·인터넷 전부 불필요 |
| 판정 로직 위치 | **폰에만**. 웹은 렌더러 | 로직 중복 제거 + 폰·웹 불일치 원천 차단 |

### 2.1 왜 펌웨어를 안 건드리는가

ESP32가 BLE와 Wi-Fi를 동시에 물려 브라우저에 직접 쏘는 안도 있다. 폰이 꺼져도
웹이 산다는 게 장점이지만 대가가 크다.

- `emg_fes_controller_wifi.ino.bak` 은 **459줄짜리 구버전**이고 현재 펌웨어는 1191줄이다.
  M-wave 검출창·blanking·RAW 스트리밍이 전부 그 이후에 붙었다. 되살리려면 700줄을
  다시 얹어야 한다.
- BLE+Wi-Fi 코엑시스턴스가 1kHz 샘플링 타이밍을 흔들 수 있다. M-wave 잠복 게이트와
  불응기(`MW_REFRACTORY_MS=21`)는 실측으로 겨우 맞춰놓은 값이다.

관찰 화면 하나를 위해 측정 신뢰성을 걸 이유가 없다.

### 2.2 왜 Flutter Web이 아닌가

Dart 코드 재사용이 장점이지만, `flutter_blue_plus` 가 웹에서 안 돌아 조건부 임포트
분기가 생기고, 산출물이 수 MB라 폰이 서빙하기 무겁고, 무엇보다 **앱과 모니터가 같은
코드베이스에 다시 묶인다** — "분리하고 싶다"는 목적과 정면으로 어긋난다.

별도 React/Vite SPA는 확장성은 좋지만 빌드 파이프라인·배포·의존성 관리가 통째로
새로 생긴다. 관찰 화면 하나에 치르는 비용치곤 과하다.

## 3. 아키텍처

```
SessionController (BLE) ──▶ LiveFatigueFeed ──┬──▶ BaseballGame        (폰: 환자)
                                              └──▶ MonitorBroadcaster
                                                        │ HTTP + WebSocket :8080
                                                        ▼
                                                   monitor.html         (노트북: 치료사)
```

### 3.1 ★ 핵심 원칙 — 웹은 판정하지 않는다

`monitor.html` 에는 σ 계산도, 존 경계 판정도, 피로 규칙도 없다. 폰의
[`SigmaTracker`](../../../flutter_app/lib/game/engine/sigma_tracker.dart) 가 계산한
z·존·스태미나를 **결과값 그대로** 실어보내고 웹은 그리기만 한다.

이유는 둘이다.

1. `SigmaTracker` 는 `fes_fatigue_spc.py` 의 이식본이고 실측 세션 3개로 파이썬 출력과
   1e-6 이내 일치가 검증돼 있다. 이 정의를 JS로 한 번 더 옮기면 검증이 갈라진다.
2. 폰 게임과 웹 모니터가 **같은 σ를 다른 존으로 표시하는 사고가 구조적으로 불가능**해진다.
   웹에 판정 코드가 없으면 어긋날 수가 없다.

부수 효과로 `monitor.html` 이 얇아져 한 파일에 계속 머무를 수 있다.

### 3.2 유닛 경계

| 파일 | 책임 | 의존 |
|---|---|---|
| `lib/monitor/monitor_frame.dart` | 프레임 모델 + JSON 직렬화 | 없음 (순수 Dart) |
| `lib/monitor/monitor_source.dart` | `LiveFatigueFeed`·`SessionController` → `MonitorFrame` 어댑터 | 위 둘 |
| `lib/monitor/monitor_broadcaster.dart` | HTTP 서버·WS 업그레이드·클라이언트 수명주기 | `dart:io`, `monitor_frame` |
| `lib/monitor/monitor_address.dart` | `NetworkInterface` → 접속 URL·세션 토큰 | `dart:io` |
| `lib/widgets/monitor/monitor_address_card.dart` | 폰에 접속 주소·토큰 표시 | Flutter |
| `assets/web/monitor.html` | 렌더링 전용 단일 페이지 | 없음 |

**외부 의존성 0.** `dart:io` 의 `HttpServer` + `WebSocketTransformer.upgrade()` 로 충분해
`pubspec.yaml` 에 추가할 패키지가 없다.

`monitor_frame.dart` 가 순수한 것이 중요하다 — 서버·소켓·Flutter 없이 직렬화와 링버퍼를
단위 테스트할 수 있어야 한다.

## 4. 프로토콜

폰이 페이지 서빙까지 겸한다. 치료사는 노트북 브라우저에 `http://192.168.0.12:8080/?k=8134`
만 입력하면 페이지를 받고 소켓이 붙는다.

| 엔드포인트 | 용도 |
|---|---|
| `GET /` | `assets/web/monitor.html` 서빙 |
| `GET /ws` | WebSocket 업그레이드 |

메시지는 전부 `{"t": "<태그>", ...}` 형태의 JSON이다.

| 태그 | 방향 | 주기 | 내용 |
|---|---|---|---|
| `hello` | 폰→웹 | 접속 시 1회 | 프로필·세션 시작시각·baseline μ/σ·최근 60초 링버퍼 |
| `tick` | 폰→웹 | 10 Hz | ts, env/rms/mdf, σ, 예측 σ, 존, 스태미나% |
| `event` | 폰→웹 | 발생 시 | 수축, 피로 판정, 존 전환, 휴식 시작·종료, 세션 시작·정지 |
| `link` | 폰→웹 | 변화 시 | BLE 연결 상태 (`disconnected`/`scanning`/`connected`/`error`) |
| `raw` | 폰→웹 | 10 Hz 패킷 | 1kHz 파형 100표본 묶음. **기본 꺼짐** |
| `sub` | 웹→폰 | 사용자 조작 | `{"t":"sub","raw":true}` — 진단 패널 펼침 = RAW 구독 |

`hello` 가 링버퍼를 함께 보내는 이유: 치료사가 세션 도중에 붙어도 빈 화면이 아니라
직전 60초 맥락을 바로 본다. 링버퍼는 **`tick` 프레임만** 담는다(10 Hz × 60초 = 600개).
`raw` 는 담지 않는다 — 구독 전에는 생성 자체를 안 하고, 진단 패널은 펼친 시점부터의
파형만 보면 된다.

`sub` 만 웹→폰 방향인데 이것은 **제어가 아니라 구독**이다. 자극·세션·강도에 손대지
않으므로 보기 전용 원칙과 충돌하지 않는다. 웹에서 오는 메시지 중 `sub` 외의 모든
것은 폰이 무시한다 — 화이트리스트 방식으로 구현한다.

대역폭은 문제가 아니다. RAW 1kHz × 2바이트 = 2 KB/s 이고 `tick` 은 그보다 훨씬 작다.

## 5. 전제조건 — BLE 단일 소유권

지금 BLE 파이프라인이 **두 벌**이다.

- [`home_page.dart`](../../../flutter_app/lib/screens/home_page.dart) 가 `flutter_blue_plus` 를 직접 다룬다
- [`session_controller.dart:101`](../../../flutter_app/lib/services/session_controller.dart) 의 `scanAndConnect()` 가 따로 있다

그 결과 `home_page.dart:1280` 이 `const GameScreen()` 을 세션 인자 없이 띄우고 있고,
`GameScreen` 은 `session == null` 이면 `MockFatigueFeed` 로 떨어진다 — **게임이 현재
목 데이터로 돌고 있다.** 이 상태로 웹 모니터를 붙이면 치료사가 가짜 σ를 본다.

같은 기기에 두 번 연결할 수는 없으므로 다음과 같이 해결한다.

**`SessionController.adopt({device, dataChar, rawChar, cmdChar})` 를 추가한다.**
home_page가 이미 열어둔 characteristic 스트림을 SessionController가 구독하는 방식이다.
게임 진입 시 재스캔·재연결이 없어 지연이 0이고, home_page 1497줄을 건드리지 않는다.
`GameScreen(session: ...)` 에 그 컨트롤러를 주입하면 게임과 모니터가 같은 실 데이터
줄기에서 돈다.

이 항목은 "웹 분리"보다 범위가 넓어 보이지만, 빼면 웹 모니터가 목 데이터를 그린다.

## 6. 실패 처리

**원칙: 모니터가 죽어도 세션은 죽지 않는다.** 포트 점유든 Wi-Fi 끊김이든 방송기
예외든, 게임과 자극은 그대로 간다. 방송기의 모든 예외는 방송기 안에서 삼키고
폰 UI에 배너로만 알린다.

| 상황 | 처리 |
|---|---|
| 웹 소켓 끊김 | 웹이 지수 백오프 재연결(0.5s → 최대 5s). 그동안 화면 전체를 **회색 처리(stale)** 하고 "연결 끊김 · 재연결 중" 배너 |
| `tick` 2초 무수신 | 소켓이 살아 있어도 stale 처리. 10 Hz 기준 20프레임 누락이면 이미 못 믿을 화면이다 |
| BLE 끊김 | `link` 이벤트로 웹에 전달. Wi-Fi 끊김과 **구분해서 표시** |
| 웹 클라이언트가 느림 | 큐를 쌓지 않고 최신 프레임만 유지(drop-oldest) |
| 포트 점유 | 8080부터 8090까지 순차 시도. 전부 실패 시 "모니터 비활성" 배너만 |
| 앱이 백그라운드로 | 웹에 "폰 화면 꺼짐" 통지 후 소켓 정리, 복귀 시 재개 |

stale 회색 처리가 특히 중요하다. **치료사가 3분 전 σ를 지금 값으로 착각하는 것이
이 화면의 최악 실패 모드다.** 마지막 값을 현재값인 척 계속 그리지 않는다.

BLE 끊김과 Wi-Fi 끊김을 구분하는 이유도 같다 — 전자는 전극·기기를 확인해야 하고
후자는 네트워크를 확인해야 한다. 조치가 다르면 표시도 달라야 한다.

## 7. 보안·개인정보

로컬 네트워크 밖으로 나가는 데이터가 없다. 클라우드·계정·인증 서버가 없다.

다만 병원 Wi-Fi에는 남이 있으므로 **랜덤 4자리 토큰**을 URL 쿼리(`?k=8134`)로 요구한다.
토큰은 **방송기가 시작될 때마다** 새로 발급된다(앱 실행 단위가 아니다 — 앱을 껐다 켜지
않아도 이전 접속자가 계속 붙어 있지 않도록). 토큰이 없거나 틀리면 `GET /` 와 `GET /ws`
모두 403이다.
암호학적 방어가 아니라 우발적 접근 차단이 목적이다 — 로컬 네트워크 한정이라는
전제 위에서 이 정도가 비용 대비 적절하다.

폰 화면에 접속 주소와 토큰을 함께 표시한다.

## 8. 테스트

| 대상 | 방법 |
|---|---|
| `MonitorFrame` 직렬화 | 단위 — 왕복 변환, 필드 누락, 존 매핑 |
| 링버퍼 스냅샷 | 단위 — 60초 초과 시 오래된 것부터 폐기, `hello` 내용 검증 |
| 백프레셔 | 단위 — 느린 소비자에 drop-oldest 적용 확인 |
| 구독 토글 | 단위 — `sub` 이전엔 `raw` 미발신, 이후 발신. `sub` 외 메시지 무시 |
| 서버 수명주기 | 통합 — 포트 점유 시 다음 포트, 전부 실패 시 예외 없이 비활성 |
| 종단 | 통합 — `SimulatorService` 로 서버 띄우고 Dart WS 클라이언트가 `hello`+`tick` 수신 |
| 렌더링 | `monitor.html` 의 **CSV 재생 모드를 유지**해 장비 없이 회귀 확인 |
| 실기기 | 수동 — iPhone + 노트북, 같은 Wi-Fi에서 세션 1회 |

`monitor.html` 이 재생 모드를 유지하는 것은 테스트 편의만이 아니다. 데모·발표에서
장비 없이 보여주는 용도로 계속 쓰인다.

## 9. 범위 밖

지금 하지 않는다.

- **QR 코드** — 주소가 짧아 타이핑 가능하다. 불편이 확인되면 그때 추가한다
- **클라우드 원격 관찰** — 전송 계층을 교체 가능하게 두되 구현하지 않는다
- **웹에서의 제어** — 시작·정지·강도는 폰에서만
- **다중 환자 동시 모니터링** — 한 폰 = 한 세션
- **home_page.dart 전면 리팩터** — §5의 `adopt` 최소 변경만 한다
