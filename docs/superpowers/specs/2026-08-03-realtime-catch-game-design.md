## 2. 컨셉

FES 자극 박자에 맞춰 날아오는 공을 **손을 쥐어(잼) 포구**하는 리듬형 바이오피드백
훈련이다. 자극이 M-wave를 유발하고, 그 진폭이 줄어드는 정도를 SPC σ로 환산해
"스태미나 게이지"로 보여준다. 3σ(관리이탈)에 처음 도달하면 강판/휴식 이닝으로
넘어간다.

목적은 재미가 아니라 훈련이다. 재미는 지속을 위한 수단이다.

## 3. ★ 핵심 설계 원칙 — 엔진은 σ를 모른다

"판정과 점수는 피로도에 영향받지 않는다"를 **주석이 아니라 타입으로** 보장한다.

`CatchGameEngine`은 `SigmaTracker`를 import하지 않는다. σ를 보는 건 화면뿐이고,
화면은 3σ에서 `engine.pause()`만 호출한다 — 엔진은 *왜* 멈췄는지 모른다. 나중에
누가 σ를 판정에 끼워넣으려면 없는 의존성을 새로 만들어야 하므로 리뷰에서 걸린다.

부수 효과로 엔진이 결정론적이 되어 유닛테스트가 가능하다(시각은 인자로 주입,
Flutter·타이머·랜덤 의존 없음).

### 4.1 σ 산출 — `fes_fatigue_spc.py`를 그대로 옮긴다

기준 구현은 `~/emgfes-data/fes_fatigue_spc.py`이고, 이 프로젝트의 SPC 결과 전부가
그 정의 위에 서 있다. `SigmaTracker`는 이를 실시간으로 재현한다.

| 단계 | 정의 |
|---|---|
| 특징 | **M-wave peak-to-peak**(`w.max()−w.min()`), 창 **5~15ms**. 면적 아님 |
| 표본 단위 | **버스트당 1점** — 버스트 첫 펄스만 (>800ms 간격으로 버스트 구분) |
| 이상치 제거 | Hampel (k=7, nσ=3) — 전극 글리치 |
| baseline | **t ∈ [20, 90]초**, `mu0 = median`, `sd0 = 1.4826 × MAD` (견고) |
| 평활 | **EWMA** `z[i] = 0.15·amp[i] + 0.85·z[i−1]` (인과적) |
| σ | `zsig = (mu0 − EWMA) / sd0` — 진폭이 떨어지면 z가 오른다 |
| 존 도달 | **5연속 지속**, 그리고 **t ≥ 90초 이후만** (`first_sustained`) |
| 품질 게이트 | `base_cv = sd0/mu0` — 너무 크면 baseline 불량 |

부가: CUSUM(`k=0.5σ`, `h=5σ`)은 조기경보용으로 정의돼 있다. MVP에서는 z만 쓰고
CUSUM은 범위 밖으로 둔다.

**설계에 미치는 결과 — 첫 90초는 baseline 구간이다.** 게이지는 "측정 중"으로
두고 강판 트리거를 무장하지 않는다. 게임 서사로는 "워밍업 이닝"이 된다. 20초
이전 구간은 baseline에서도 제외된다(전극 안정화).

`ControlChart`는 쓰지 않는다 — 평균·표준편차 6점이라 중앙값·MAD·EWMA·지속판정
어느 것도 맞지 않는다. 기존 서비스는 **전혀 건드리지 않는다.**

### 4.2 전제조건 — 펌웨어 수정 (완료)

`MW_REFRACTORY_MS` 40 → **21**, `MW_WINDOW_END_MS` 30 → **15**. `data` 브랜치 실측 근거:

- `master_pulses.csv` 123,182 펄스: ISI 중앙값 **31ms**, p1=26ms, 잠금세션 최소 23ms.
  옛 refractory 40ms는 이 간격보다 커서 잠금 세션에서 격번으로만 검출됐다(~50%).
  M-wave 표본이 절반이 되고, blanking도 `mwArtifactAtMs`를 키로 삼으므로 함께
  절반만 걸려 RMS/MDF가 자극 스파이크에 오염됐다.
- RAW 앙상블 평균(`raw_20260717_033307` n=270, `raw_20260717_141940` n=2042):
  M-wave는 **13~15ms에 이미 바닥**이고, **24~30ms는 다시 상승**한다 — 다음 펄스가
  다가오는 램프다. 즉 **옛 5~30ms 창은 다음 자극을 창에 섞고 있었다.**
- 15ms는 오프라인 `s[o+5:o+15]`와 정확히 같다. 실시간 값과 분석 결과가 같은 정의
  위에 서게 된다.

### 4.3 남는 불일치 (인지하고 감수)

펌웨어 실시간 값과 오프라인 값은 **수치가 같지 않다**:

| | 오프라인 | 펌웨어 |
|---|---|---|
| 전처리 | 20~450Hz 4차 Butterworth **filtfilt**(비인과) | 원 centered (필터 없음) |
| artifact 임계 | 필터 후 \|s\|>400 | 원신호 \|centered\|>1000 |

`filtfilt`는 미래 표본을 쓰므로 실시간에서 구현 불가다. 따라서 절대값 비교는
불가하고, **z만 비교 가능하다** — SPC가 자기기준(baseline도 같은 소스)이라
z 스케일은 유지된다. 이전 데이터와 진폭 절대값을 직접 비교해서는 안 된다.

**기존 서비스는 한 줄도 건드리지 않는다.** `FatigueEngine`·`ControlChart`는
평균±표준편차 기반이라 이 방법(중앙값·MAD·EWMA·5연속 지속)과 맞지 않고, 기존
임상 화면이 의존한다. 게임은 `lib/game/` 안에서 `SigmaTracker`로 자립한다.
`SessionController`는 구독만 한다.

## 5. 근피로(σ)의 역할 — 딱 두 가지

**(a) 시각 연출만**
- 배경 그라데이션·조명·글러브 림라이트를 현재 존 색으로 틴트
- 상단 미니 게이지(반원 + σ 숫자 + 존 라벨)
- 존이 오를수록 어두워짐 (색·투명도만)
- ※ 판정창·점수·투구속도에 절대 영향 없음

**(b) 3σ 강판/휴식**
- z가 3σ에 처음 도달하면 진행 정지 + 전체화면 오버레이
  "🛑 투수 교체 — 휴식 이닝" + 쿨다운 카운트다운(20초)
- 오버레이 안에 **풀 게이지 + 타임라인 + 리드타임 통계** 표시 (쉬는 동안 자기 곡선을 본다)
- 점수 페널티 없음. 이닝은 강판이 나눈다(시작 1회)
- 휴식 후: baseline을 재설정하지 않고 z 관측을 계속한다. 회복되면 z가 내려간다.

**재발동 규칙 (히스테리시스).** 쿨다운이 끝난 시점의 z로 갈린다:
- `z < 2σ` → 다음 이닝 재개. 강판 트리거를 다시 무장한다.
- `2σ ≤ z < 3σ` → 재개하되 무장은 z가 2σ 아래로 내려갈 때까지 미룬다.
- `z ≥ 3σ` (휴식해도 회복 안 됨) → 재개하지 않고 **세션 종료 권유** 화면으로 간다.
  "오늘은 여기까지" + 결과 시트. 무리한 재개를 막는 것이 이 이벤트의 목적이다.

무장 해제 없이 곧바로 재트리거하면 z가 3σ에 머무는 동안 오버레이가 무한 반복된다.
반드시 2σ 아래로 내려갔다 와야 다시 걸린다.

## 7. 판정 — 고정, σ 무관

| | 창 | 점수 |
|---|---|---|
| Perfect | ±120ms | 100 |
| Good | ±250ms | 50 |
| Miss | 그 밖 · 무입력 · 빈 스윙 | 0, 콤보 리셋 |

- **박자** = `st.isStimulating` 상승엣지 (실측 버스트 주기 1621.9ms).
  자극이 없으면 `TimerBeatSource(1.6s)`로 폴백(시뮬레이터·건강인 검증용).
- **입력** = ENV 수축 onset. 안정구간 baseline(μ_rest + k·σ_rest) 상향 통과 순간.
  화면 탭은 디버그 입력으로만 남긴다.
- 콤보는 표시만. 점수 배율 없음.

**타이밍 해상도 주의:** ENV는 5Hz(200ms)로 큐에 쌓이고 `envLast`는 10Hz로
갱신된다. 따라서 실질 판정 해상도는 ~100ms다. ±120/±250ms는 이보다 넉넉하다.
더 정밀한 판정이 필요하면 RAW 1kHz 스트림을 붙인다(범위 밖).

## 8. 캘리브레이션 — 두 종류

σ와 입력 임계는 출처가 달라 단계가 갈린다.

1. **안정 baseline (입력용)** — "힘 빼고 쉬세요" 8초 → rest ENV의 μ,σ →
   수축 onset 임계 = `μ_rest + 3·σ_rest`. 3은 상수로 노출해 실사용에서 튜닝한다
   (너무 낮으면 잡음이 포구로 오판되고, 너무 높으면 약한 수축을 놓친다).
2. **fresh baseline (σ용)** — 워밍업 이닝. **20~90초** 구간의 버스트별 M-wave
   peak-to-peak로 `mu0`(중앙값)·`sd0`(1.4826×MAD) 확정. 0~20초는 전극 안정화로
   버린다. 90초 전까지 게이지는 "측정 중", 강판 트리거 비무장(§4.1).

SPC 원칙 1(개인 자기기준)을 UI로 구현한 것이다. 게이지의 100%는 언제나 그 사람
자신의 초기 상태다.

**σ 없이도 게임은 성립한다.** M-wave가 전혀 안 잡히면(자극 없음·전극 문제·펌웨어
이상) fresh baseline이 확정되지 않는다. 이때 게이지는 "측정 중"으로 두고 강판
트리거를 비활성화하되, **포구 게임은 정상 진행한다** — 판정·점수는 애초에 σ와
무관하기 때문이다(§3). σ는 얹히는 층이지 게임의 전제가 아니다.

## 9. 렌더링 — flutter_cube

히어로(공·글러브)는 `flutter_cube` 절차적 메시, HUD·게이지·배경은 2D 위젯.
`CatchGameEngine`은 렌더러에 무관하다.

**검토 후 배제한 대안:** `flutter_3d_controller` + GLB. 보유 모델
(Tripo 정적 2종, Meshy biped 리깅 1종)은 클립이 없거나(정적) 인간형 걷기·달리기
클립뿐이고 손가락 조인트가 없어 "쥐기"를 표현할 수 없다. 셋 다 95만 삼각형·
23~36MB로 모바일 예산 밖이다.

flutter_cube를 쓰면 `Mesh.vertices`가 가변 `List<Vector3>`라 매 프레임 손가락부를
힌지 회전시켜 글러브를 실제로 접을 수 있다 — GLB 모프 수술이 불필요해진다.
대신 CPU 정점 변환이라 예산이 ~1k–5k 삼각형이다(스파이크가 3,456을 "과부하"로
라벨). 공은 2D 오버레이가 아니라 3D 씬에 넣는다 — 원근이 공짜로 나온다.

## 13. MVP 범위

## 14. 성공 기준

- 시뮬레이터만으로 캘리브레이션 → 게임 → 강판 → 재개 → 종료 전 흐름 플레이 가능.
- `CatchGameEngine`·`SigmaTracker`가 결정론적 유닛테스트로 검증됨
  (Perfect/Good/Miss, 콤보 증감, baseline 확정, z 계산, t1/t2/t3 인과적 기록,
  강판 히스테리시스 3분기, 3σ 지속 시 오버레이가 반복되지 않음).
- `CatchGameEngine`이 `SigmaTracker`를 import하지 않음(테스트로 고정).
- M-wave가 한 번도 안 들어와도 게임이 처음부터 끝까지 플레이됨(게이지만 "측정 중").
- iPhone(2)에서 빌드·실행 확인.
- 실기기에서 M-wave 검출률이 자극당 ~100%인지 확인(펌웨어 수정 검증).

## 15. 열린 질문

- **M-wave 잠복 변동 vs 5~15ms 창.** 잠복이 세션마다 3~11ms로 흔들린다는 기록이
  있다. 잠복 11ms면 M-wave 꼬리가 15ms를 넘어 잘릴 수 있다. 오프라인 방법이 이미
  5~15ms로 확정돼 있어 그대로 맞췄지만, 실기기에서 p2p가 창 경계에 눌리는지
  확인할 필요가 있다.
- **90초 baseline이 게임 흐름에 맞는가.** 매 판 첫 90초는 σ가 없다. 이닝 구성상
  자연스러운지, 아니면 이전 세션 baseline을 재사용하는 경로를 둘지.
- **품질 게이트 `base_cv` 임계값.** `sd0/mu0`가 얼마를 넘으면 "baseline 불량"으로
  보고 σ를 포기할지. 오프라인 스크립트는 값을 기록만 하고 자르지 않는다.
- 강판 쿨다운 20초가 적절한지(실사용 튜닝).
- 글러브 힌지 축·접힘 각도(절차적 메시라 코드 상수, 눈으로 튜닝).
