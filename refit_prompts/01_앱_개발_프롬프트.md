# [앱 개발 프롬프트] RE-FIT Play — Flutter

> 실행 전 `00_공통_컨텍스트_프롬프트.md`를 먼저 붙여넣을 것. 아래는 그 컨텍스트를 전제로 한다.

---

너는 의료 재활 소프트웨어를 만드는 시니어 Flutter 개발자다. **RE-FIT Play** 앱을 만든다. 사용자는 손을 스스로 움직일 수 없는 **완전마비 환자**이고, 이 앱은 매일 쓰는 물건이 되어야 한다.

## 0. 작업 원칙

- 공통 컨텍스트의 **하드 제약 8개와 상수 테이블을 그대로 지킨다.** 임의 변경 금지.
- 신호 처리 정확도 > 게임 연출. 둘이 충돌하면 연출을 줄인다.
- 추측으로 상수를 만들지 않는다. 값이 필요한데 정해지지 않았으면 `// TODO(P0): 실측 확정` 주석과 함께 상수로 분리하고 보고한다.
- 단계별로 만들고 각 단계 끝에 **실행 가능한 상태**를 유지한다. 한 번에 전부 쓰지 않는다.
- 각 단계가 끝나면 무엇을 만들었고 무엇이 검증되지 않았는지 보고한다.

## 1. 기술 스택

| 영역 | 선택 |
|---|---|
| 프레임워크 | Flutter (최신 stable), Dart 3 |
| 상태관리 | Riverpod |
| BLE | flutter_blue_plus |
| 로컬 DB | drift (SQLite) |
| 게임 렌더링 | Flame |
| 백엔드 연동 | supabase_flutter |
| 신호 처리 | 순수 Dart (외부 DSP 패키지 없이 직접 구현) |

신호 처리를 순수 Dart로 쓰는 이유는 오프라인 Python 파이프라인과 1:1 대조 테스트를 하기 위해서다. 블랙박스 라이브러리를 쓰면 대조가 불가능해진다.

## 3. 단계별 작업 순서

### 단계 1 — 신호 엔진 (가장 먼저, 가장 중요)

UI 없이 순수 Dart로 `lib/signal/` 전체를 구현한다. 입력은 `Stream<(int timeMs, int adc)>`, 출력은 버스트 단위 결과다.

```dart
class BurstResult {
  final int index;
  final double tSeconds;
  final double p2p;             // Hampel 적용 후
  final double fatiguePct;      // 적응형 기준
  final bool contractionOk;
  final int eventsInBurst;
  final bool reliable;
  final int levelSegmentIndex;
  final int stimOnsetMs;        // 위상 고정된 실제 자극 시점
}
```

**검증이 이 단계의 산출물이다.** `emgfes-data/subject_*/raw_*.csv`를 읽어 스트림으로 흘려보내는 테스트 하네스를 만들고, 공통 컨텍스트 8장의 기대치와 대조한다.

| 테스트 | 기대 |
|---|---|
| 주기 추정 | 1618ms 근방 |
| 버스트 수 | 세션당 중앙 337 |
| 신뢰도 통과 | 88세션 중 58 |
| 적응형 임계 검출 | 58 중 47 |
| Hampel 효과 | 글리치 세션에서 최대 피로도가 유의하게 낮아짐 |

숫자가 안 맞으면 파라미터를 억지로 맞추지 말고 **어디가 왜 다른지 보고**한다.

### 단계 2 — BLE + 자극 제어

기기 스캔·연결·자동 재연결, raw 샘플 스트림 수신, 자극 ON/OFF 명령. **BLE가 끊기면 자극이 자동으로 꺼져야 한다**(펌웨어 페일세이프와 앱 양쪽에서). 앱 프로세스가 죽어도 자극이 계속되면 안 된다.

### 단계 3 — 세션 상태머신

```
idle
 → connecting          기기 연결
 → attachmentCheck     부착 체크 (3항목)
 → intensityWizard     강도 설정 마법사
 → syncing             자극 주기 동기화 + A_ref 워밍업 (30초)
 → playing             게임
 → ending              종료 처리
 → report              결과 화면
```

각 전이 조건과 실패 처리를 명시적으로 구현한다. 어느 단계에서든 중단 버튼으로 즉시 `ending`으로 갈 수 있다.

**부착 체크 (3항목)**

| 항목 | 자동 판정 |
|---|---|
| EMG 전극 | 무자극 1–2초 baseline noise RMS + DC offset. 임계 초과 시 재부착 안내 |
| 자극 패드 | 최저 강도 테스트 펄스 1회 → M-wave 검출 여부 |
| 기기 상태 | 배터리, BLE 신호 세기 |

각 항목에 **부착 위치 일러스트**를 붙인다(플레이스홀더 에셋으로 시작). 텍스트만으로는 매번 실패한다.

**강도 설정 마법사**

낮은 단계부터 한 단계씩 올린다. 각 단계에서 자동으로 events/burst를 측정하고, 사용자에게 "움직임이 느껴지나요?"(안 느껴짐 / 적당함 / 너무 셈)를 묻는다. **목표는 `events/burst >= 10`을 만족하는 최소 강도.** 결과를 `intensity_profiles`에 저장하고 다음 세션 기본값으로 쓴다. 세션 중에는 하향만 가능하고 상향은 불가.

**동기화 구간 (30초)**

자극 주기 검출 + 위상 고정 + A_ref 워밍업을 여기서 한다. 사용자에게는 **튜토리얼 라운드**로 보여준다. "기기 신호를 맞추고 있어요" 같은 대기 화면을 따로 만들면 이탈한다.

### 단계 4 — 게임 코어 루프

**이 앱에서 가장 어려운 부분이다.** 게임은 자극 주기에 위상 잠겨 있어야 한다.

```
매 주기 (약 1618ms):

  t = stimOnset − 300ms   화면의 손이 쥐어지기 시작 (큐)
                          → 환자가 "쥔다"고 의도할 시간을 준다
  t = stimOnset           FES 발화
  t = stimOnset + 5~15ms  M-wave 검출 → contractionOk 판정
  t = 판정 직후            성공 시: 손 완전히 쥠 + 햅틱 + 사운드 + 이펙트
                          실패 시: 손이 힘없이 멈춤 (부정적 연출 아님, 담담하게)
  t = stimOnset + 591ms   자극 OFF → 화면 손 펴짐
  t = 다음 주기            반복
```

핵심 요구사항:

- **큐는 자극보다 `CUE_LEAD_MS`(300ms) 먼저 나와야 한다.** 늦으면 훈련 효과가 사라진다.
- 위상 드리프트를 매 N버스트마다 보정한다. 누적 오차가 `PHASE_DRIFT_TOLERANCE_MS`(100ms)를 넘으면 로그를 남기고 재동기한다.
- **드리프트 진단 로그를 반드시 남긴다.** 위상이 밀려도 게임은 정상으로 보이기 때문에, 로그가 없으면 효과만 조용히 사라지는 실패를 아무도 감지하지 못한다.
- 프레임 드랍이 큐 타이밍에 영향을 주면 안 된다. 큐 스케줄링은 렌더 루프가 아니라 별도 타이머 기반으로.

**템포는 바꿀 수 없다.** 자극 주기에 묶여 있어 리듬게임식 난이도 상승이 불가능하다. 재미는 아래에서 만든다.

| 축 | 방법 |
|---|---|
| 시각 변주 | 스테이지마다 배경·캐릭터·오브젝트 교체 |
| 목표 변주 | "오늘은 100번 물주기" / "50개 수확" — 같은 반복에 다른 의미 |
| 서사 | 세션마다 이야기가 조금씩 진행 |
| 즉각 피드백 | 매 성공마다 사운드 + 햅틱 + 이펙트. 세션당 약 340번의 작은 성공 |
| 누적 표현 | 종료 시 "오늘 340번 쥐었어요" |

**피로 게이지를 별도 UI로 만들지 않는다.** 피로가 진행되면 p2p가 떨어지고 → 수축 성공률이 떨어지고 → 화면에서 손이 잘 안 쥐어진다. 피로는 게임 안에서 저절로 표현된다. 퍼센트 숫자는 앱 어디에도 띄우지 않는다(숫자는 웹에만 있다).

MVP는 **전체 손 쥠/폄 한 종류**다. 손가락 개별 제어는 다채널 자극이 필요하므로 범위 밖이다. 화면에서는 손가락이 접히는 모습을 보여주되 실제 자극은 grasp 한 채널이다.

### 단계 5 — 종료 조건

우선순위대로 평가한다.

| 순위 | 조건 | 코드 |
|---|---|---|
| 1 | 적응형 피로도 ≥ 임계, 연속 `FATIGUE_CONSECUTIVE_BURSTS` 유지 | `fatigue_threshold` |
| 2 | 최근 `SUCCESS_RATE_WINDOW`(50) 버스트 성공률이 초기 대비 `SUCCESS_RATE_DROP_RATIO`(40%) 이하 | `success_rate_drop` |
| 3 | 세션 시간 `SESSION_MAX_MIN`(15분) 도달 | `timeout` |
| — | 스테이지 목표 달성 | `game_complete` |
| — | 사용자 중단 버튼 | `user_stop` |
| — | 서버 원격 중단 명령 수신 | `remote_stop` |
| — | 신뢰도 붕괴 `SIGNAL_LOST_TIMEOUT_S` 지속 | `signal_lost` |
| — | BLE·전원 끊김 | `device_disconnect` |

> 2번과 3번 백업 조건은 **반드시** 구현한다. 적응형 기준은 보수적이라 실측에서 58세션 중 47세션에서만 임계가 걸렸다. 백업이 없으면 5~6세션에 하나꼴로 종료가 안 걸린다.

**종료 화면은 3줄뿐이다.** "오늘 340번 쥐었어요 / 9분 완주 / 내일도 같은 시간에 만나요". 그래프도 퍼센트도 없다.

### 단계 6 — 기록·캘린더

월 캘린더에 점 색 = 그날 게이지 등급, 점 크기 = 반복 횟수. 연속 수행일, 주간 목표 달성률. 세션 상세는 앱에서 **반복 횟수 / 수행 시간 / 종료 이유(사용자 언어)** 3개만 보여준다.

뱃지는 첫 완주, 7일 연속, 누적 1만 회처럼 **횟수·지속 기반**으로 만든다. 피로도 수치 기반 뱃지는 개인차가 커서 불공정하므로 만들지 않는다.

### 단계 7 — 로컬 저장 + 동기화

raw는 저장하지 않는다. **버스트 단위 지표만** 남긴다(세션당 약 340행, 수십 KB). drift 스키마는 공통 컨텍스트 6장의 `sessions` / `session_series` / `session_events`와 컬럼을 맞추고 `synced` 플래그를 추가한다.

업로드 정책:
- 세션 중: `session_live` 행을 2–5초 간격 upsert (웹 라이브 뷰용)
- 세션 종료: 요약 + 시계열 일괄 업로드
- 실패 시 로컬 큐 보관 후 재시도. **오프라인에서도 훈련은 끝까지 되어야 한다.**

원격 중단 명령은 Supabase Realtime으로 구독하고, 수신 즉시 자극을 끈 뒤 `remote_commands`에 `acked_at` / `executed_at`을 기록한다.

### 단계 8 — 설정·연결

기기 페어링, 강도 프로파일 확인, 알림 시간, **치료사 초대 코드 입력**(6자리 → `care_relations` 생성).

## 4. UI 설계 원칙

1. 첫 실행부터 게임 시작까지 **3분 이내**
2. **한 손 조작.** 주요 버튼은 화면 하단 ⅓ 안에, 최소 44pt
3. **숫자 대신 상태.** 퍼센트를 띄우지 않는다
4. **소리와 햅틱을 시각과 동등하게.** 화면을 계속 응시하기 어려운 사용자가 있다
5. **실패 표현 금지.** 피로 임계 도달은 실패가 아니라 "오늘 목표 달성"이다. 문구·사운드·뱃지 전부 이 프레임을 지킨다
6. **오프라인 우선**
7. **중단 버튼 상시 노출** — 누르면 즉시 자극 OFF

## 5. 안전 요구사항

- 강도 상한 하드코딩, 세션 중 하향만 허용
- 통증 중단 버튼 → 즉시 자극 OFF (다른 어떤 처리보다 우선)
- BLE 끊김 시 자극 자동 OFF
- 연속 세션 제한 및 최소 휴식 간격
- 최초 실행 시 주의사항 동의
- **로컬 자동 종료가 언제나 1차 안전장치.** 네트워크에 의존하는 기능은 안전의 1차가 될 수 없다

## 6. 완료 기준

- [ ] 오프라인 raw CSV 회귀 테스트가 공통 컨텍스트 8장 기대치를 통과
- [ ] 큐–자극 위상 오차가 세션 내내 100ms 이내로 유지되고, 초과 시 로그가 남는다
- [ ] 종료 조건 8종이 전부 구현되고 각각 재현 테스트가 있다
- [ ] 네트워크를 끊은 상태에서 세션이 끝까지 진행되고, 연결 복구 시 업로드된다
- [ ] BLE를 강제로 끊었을 때 자극이 꺼진다
- [ ] 앱 어디에도 피로도 퍼센트 숫자가 노출되지 않는다
- [ ] 부착 체크·강도 마법사를 통과하지 않으면 게임에 진입할 수 없다
