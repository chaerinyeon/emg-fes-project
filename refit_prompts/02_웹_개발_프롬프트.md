# [웹 개발 프롬프트] RE-FIT Care — 치료사·관리자 대시보드

> 실행 전 `00_공통_컨텍스트_프롬프트.md`를 먼저 붙여넣을 것. 아래는 그 컨텍스트를 전제로 한다.

---

너는 의료 데이터 대시보드를 만드는 시니어 프론트엔드 개발자다. **RE-FIT Care** 웹을 만든다. 사용자는 재활 치료사와 관리자다.

치료사는 담당 환자 5–30명을 주 1–2회 데스크톱에서 확인한다. 궁금한 건 둘뿐이다 — **누가 안 하고 있나, 누가 이상한가.** 이 두 질문에 3초 안에 답하지 못하는 화면은 실패다.

## 0. 작업 원칙

- 공통 컨텍스트의 **하드 제약 8개**를 지킨다. 특히 제약 6(환자 간 절대 피로% 비교·순위 금지)은 UI 설계 전체에 영향을 준다.
- 표시하는 모든 숫자는 공통 컨텍스트의 정의를 따른다. 새 지표를 임의로 만들지 않는다.
- 단계별로 만들고 각 단계 끝에 배포 가능한 상태를 유지한다.

## 1. 기술 스택

| 영역 | 선택 |
|---|---|
| 프레임워크 | Next.js (App Router) + TypeScript |
| 스타일 | Tailwind CSS + shadcn/ui |
| 데이터 | Supabase (Postgres + Auth + Realtime) |
| 차트 | Recharts |
| 상태 | TanStack Query + Supabase Realtime 구독 |

## 2. 페이지 구조

```
/login
/patients                     환자 목록 (치료사 홈)
/patients/[id]                환자 상세
/patients/[id]/sessions/[sid] 세션 리포트
/live/[sessionId]             라이브 세션 뷰
/alerts                       알림·이상 목록
/admin                        관리자 (계정·초대코드·기기·내보내기)
```

## 3. 단계별 작업 순서

### 단계 1 — 인증·권한

Supabase Auth. 역할은 `therapist` / `admin` 둘. **치료사는 `care_relations`에 연결된 환자만 조회할 수 있다.** Postgres RLS로 강제한다. 프론트에서만 거르는 방식은 금지.

### 단계 2 — 환자 목록 (치료사 홈)

| 컬럼 | 내용 |
|---|---|
| 환자 | 익명 코드 + 표시명 |
| 최근 세션 | 날짜 + 경과일 |
| 7일 수행률 | `5/7` |
| 최근 반복 횟수 | `340회` |
| 최근 게이지 | 등급 색 + 값 |
| 상태 | 진행 중 / 정상 / 미수행 / 신호 불량 |

- **진행 중인 세션은 목록 최상단에 라이브 배지**로 뜨고, 클릭하면 `/live/[sessionId]`로 간다
- 정렬·필터: 미수행 일수, 신호 품질 경고, 최근 활동
- **환자 간 피로도 순위 정렬 기능은 만들지 않는다.** 개인차(피험자별 중앙 11~66%)가 피로 차이보다 커서 순위 자체가 의미가 없다. 정렬은 수행 여부와 신호 품질 기준으로만 제공한다

이 화면은 `sessions` 테이블 조회만으로 그려져야 한다. `session_series`를 읽으면 안 된다.

### 단계 3 — 세션 리포트 (이 웹의 존재 이유)

**"어느 정도로 얼마나 피로해져서 멈췄는지"가 여기서 답해진다.** 가장 공들일 화면이다.

**① 게이지 궤적 그래프**
- x = 경과 시간, y = 피로도%(적응형 기준)
- 마커 3종: `onset`(첫 임계 도달), `level_change`(레벨 변화 지점), 종료 시점
- **수축 성공률 궤적을 같은 축에 겹쳐 표시** — 피로 진행이 실제 동작 실패로 이어졌는지 확인하는 용도. 이 두 곡선의 관계가 치료사가 실제로 보는 것이다

**② 중단 정보 블록**

| 항목 | 예시 |
|---|---|
| 중단 시각 | 시작 후 8분 12초 |
| 중단 시점 게이지 | 19% (적응형) |
| 중단 사유 | `fatigue_threshold` — 색·아이콘 포함 |
| onset 시각 | 시작 후 3분 02초 |
| 총 반복 횟수 | 298회 |
| 수축 성공률 | 초기 96% → 종료 61% |

**③ 신뢰도 배지**
events/burst 중앙값, 검출률, 레벨 변화 횟수, 등급(A/B/C). **등급 C이면 그래프 위에 경고 오버레이를 덮는다.** 신뢰할 수 없는 데이터를 신뢰할 수 있는 것처럼 보여주면 안 된다.

**④ 중단 사유 표시**

| 코드 | 색 | 치료사 액션 힌트 |
|---|---|---|
| `fatigue_threshold` | 주황 | 정상. 강도·시간 조정 검토 |
| `success_rate_drop` | 주황 | 정상. 전극 상태도 함께 확인 |
| `game_complete` | 초록 | 정상. 목표량 상향 검토 |
| `timeout` | 파랑 | 강도 상향 검토 |
| `user_stop` | 회색 | 통증·불편 확인 |
| `remote_stop` | 보라 | 사유 메모 필요 |
| `signal_lost` | 빨강 | 전극 교체·부착 재교육 |
| `device_disconnect` | 빨강 | 기기 점검 |

**피로로 멈춘 것과 장비 문제로 멈춘 것이 한눈에 구분되어야 한다.** 이게 안 되면 치료사의 모든 해석이 오염된다. 색만으로 구분하지 말고 아이콘과 텍스트를 함께 쓴다(색각 이상 고려).

### 단계 4 — 환자 상세

- 요약 카드 4개: 총 세션 수, 누적 반복 횟수, 4주 수행률, 현재 강도 레벨
- 세션 캘린더 히트맵
- 추이 차트: 세션별 최고/종료 게이지, onset 시각, 반복 횟수
- 강도 프로파일 변화 이력 — 회복 또는 전극 상태 변화의 간접 신호라 치료사에게 의미가 있다
- **같은 환자의 시간 변화만 비교한다.** 다른 환자와의 비교 UI는 만들지 않는다

### 단계 5 — 라이브 세션 뷰

앱이 세션 중 2–5초 간격으로 `session_live` 행을 upsert한다. 웹은 Supabase Realtime으로 구독한다.

| 표시 | 내용 |
|---|---|
| 경과 시간 / 반복 횟수 | 실시간 카운트 |
| 게이지 | 적응형 현재값 + 최근 2분 추이 |
| 수축 성공률 | 최근 50버스트 |
| 신호 품질 | events/burst, 검출률 |
| 연결 상태 | 마지막 업데이트로부터 경과 시간 |

**마지막 업데이트가 15초 이상 끊기면 "연결 확인 안 됨"으로 명확히 표시한다.** 멈춘 값을 현재 값처럼 보여주는 게 이 화면에서 가장 위험한 실패다.

### 단계 6 — 원격 중단

치료사가 중단을 누르면 `remote_commands`에 행이 생기고, 앱이 Realtime으로 받아 BLE로 자극을 끈다. **네트워크가 끊겨 있으면 명령이 도달하지 않으므로 전달 상태를 반드시 표시한다.**

| 상태 | 웹 표시 |
|---|---|
| `sent` | "중단 요청 전송" |
| `acked` | "앱이 요청을 받았습니다" |
| `executed` | "자극이 중단되었습니다" ← 여기까지 와야 완료 |
| 5초 내 무응답 | **"전달되지 않았습니다. 환자에게 직접 연락하세요"** (경고 스타일) |

- 중단 버튼은 오조작 방지를 위해 확인 단계를 둔다
- 누가 언제 눌렀는지 `session_events`에 `actor`와 함께 남긴다
- **이 기능이 안전장치처럼 보이게 만들지 않는다.** 1차 안전장치는 앱의 로컬 자동 종료다. UI 문구에서 이 위계를 흐리지 말 것

### 단계 7 — 알림

3일 이상 미수행, `signal_lost`·`device_disconnect` 반복 발생, 수축 성공률 급락. 각 알림에서 해당 환자·세션으로 바로 이동할 수 있어야 한다.

### 단계 8 — 관리자

계정 관리, **초대 코드 발급**(6자리, 만료 7일, 1회용 → `invite_codes`), 기기 등록·배정, CSV 내보내기(연구용), 앱·펌웨어 버전 현황.

## 4. 데이터 표시 규칙

- 피로도는 **전부 적응형 기준**이다. 전역 기준 값은 화면에 노출하지 않는다(DB에는 참고로 남길 수 있다)
- 신뢰도 등급 C인 세션의 수치는 **회색 처리 + 경고 아이콘**을 붙인다
- 절대 피로%를 성과 지표나 목표치로 쓰지 않는다. 보고는 **개인 내 시간 변화, onset, 반복 횟수, 성공률** 중심
- 환자 식별정보는 최소한만. 목록·차트의 기본 표기는 익명 코드

## 5. 성능 요구

- 환자 목록은 `sessions` 단일 테이블 조회로 그린다
- `session_series`(세션당 약 340행)는 세션 리포트에서만 읽는다
- 라이브 뷰는 Realtime 구독만 쓰고 폴링하지 않는다

## 6. 완료 기준

- [ ] 치료사가 담당하지 않는 환자 데이터를 API로 직접 요청해도 RLS에서 차단된다
- [ ] 세션 리포트에서 중단 사유가 피로 계열과 장비 계열로 명확히 구분된다
- [ ] 신뢰도 C 세션이 경고 없이 표시되는 경로가 없다
- [ ] 라이브 뷰에서 업데이트가 끊기면 15초 내에 사용자가 그 사실을 안다
- [ ] 원격 중단의 4가지 전달 상태가 전부 UI에 반영된다
- [ ] 환자 간 절대 피로도를 비교·정렬하는 UI가 어디에도 없다

## 7. 지금 시작할 것

**단계 1(인증·RLS)과 단계 2(환자 목록)부터 시작한다.** 실제 데이터가 없으면 공통 컨텍스트 6장 스키마에 맞는 시드 데이터를 만들되, 값은 실측 범위(세션 중앙 9.3분, 버스트 337개, 신뢰도 통과율 약 66%, 적응형 피로도 중앙 19%)를 따르게 하라.
